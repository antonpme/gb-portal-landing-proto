Playground layouts

Six ways to build the same block, so one of them can be chosen and the rest thrown away. F stands first because it is the only one that was not invented here: it is what ten design systems were found doing when they were read on 29 August, layout and controls both, and it now carries the control rule approved on 31 August, read out of one object rather than typed into the renderer. The five under it are the earlier attempts, kept for comparison. A, B and C hold the axes and the specimen identical and change only the arrangement. D takes A's arrangement and changes the controls instead: its panel is rendered from a schema, and each axis gets the control its shape asks for. E puts C's colours and frame around D's schema and gives every short set a row of buttons instead of a row of words. Nothing on this page is in the system yet, and no showcase wears any of it.

Window width right now: measuring. The specimen is the live button organism at that width.

Variant F

F · the unified rule: switch for yes and no, select from five, toggle when the labels fit the budget, select otherwise

The layout is what ten systems already agree on, read off their live pages on 29 August: one card, lifted off the sheet by its own shadow, with the specimen fluid on a white stage at the left and a narrow grey rail of controls at the right, a single hairline between them, and the markup folded into the card's footer band. The rule over the controls is the one approved on 31 August and it now weighs three things about an axis, in this order. Its nature: yes or no is a switch, free text is a field. Its count: five values or more is our Select, because that is more than a person reads at a glance. And its budget: a set of two to four values is the toggle button only if the whole track it would draw — every label in caps at eleven, the padding on both sides of each, the gaps, the inset and the hairline — can be paid for on one row of the rail at the width the rail has. Colour is the axis that proves it: Primary, Secondary and Inverse are three short words and they cost more than the 271 a 320 rail has to spend, so Colour is drawn as a Select rather than as a toggle folded onto a second line. The sum is done from the schema's own strings before anything is rendered, and it is done again whenever the rail changes width, so the same axis can be a toggle at one size and a Select at another. An axis that does not apply is removed rather than greyed, the rare ones are behind one More, and Light or Dark left the rail for the stage it changes. One control here is a placeholder: the switch is a plain browser checkbox, because the system has no Switch until one is taken out of Figma and measured, and Figma is not open to us yet.

Variant F, second component

The same card, on a field

The same renderer given the field, because a rule that serves one component proves nothing. Look has five values and State has six, so both are our Select by the count. Type has three, so the count sends it to the toggle and the budget decides whether it stays there: it is only asked of the two looks that have a choice to make. Required is yes or no, so it is the placeholder switch. The error text exists only while the state is Error. Nothing else changes: the card, the rail, the rule and the footer band are the ones above.

Variant A

The panel and the stage

Axes in a narrow white panel on the left, stage on the right taking the rest. The panel is a list you read down; the stage is the only large surface in the block.

Variant B

The stage over a strip

Stage across the full width, axes under it in one strip. It puts the specimen first and the controls second, which is the opposite of the reading order the other two keep, and that is the thing to judge here.

Variant C

The console and the canvas

The axes are a console: one grey block on the left that reads as an instrument rather than as page text. The stage is framed and wears a head bar that names what is standing on it and holds the ground switch.

Variant D

The panel built by rule

Variant A again, so the layout is not what is being compared: the difference is that the panel is rendered from a schema and each axis gets the control its shape asks for. Short sets are a segment, five or more are a Select, a boolean is a segment of two. Icon position is not drawn until there is an icon, and the two axes nobody sets first are under More. Size moved off the Select on 29 August: four values is not a long list.

Variant D, second component

The same panel, on a field

The same renderer and the same rules, given the field instead of the button, which is the point of a schema: a showcase describes its component and gets a panel. Label style is only drawn for the three looks that have one, so the phone, the one time code and the password never offer a choice that does not exist.

Variant E

E · C colours, D logic, one control per axis type

C's console and framed stage, D's schema, and the control rule as it now stands: a short named set is a row of buttons with one pressed, a Select is for a long list, free text is a field. There is no Select in this panel at all: State has five values and still reads as buttons over two rows. Icon position, and the glyph under More, are not drawn until there is an icon.

Variant E, second component

The same panel, on a field

The same renderer given the field. Look has five values, so it is the one Select on the bench. State has six, and it is drawn twice on purpose, as a Select and as a row of buttons, both moving the same axis: the question of which reads better on a long set is answered by looking at them rather than by arguing. Type is only asked of the two looks that have a choice, and the error text only exists while the state is Error.
