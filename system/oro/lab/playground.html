Playground layouts

Six ways to build the same block, so one of them can be chosen and the rest thrown away. F stands first because it is the only one that was not invented here: it is what ten design systems were found doing when they were read on 29 August, layout and controls both, and it now carries the control rule approved on 31 August, read out of one object rather than typed into the renderer. The five under it are the earlier attempts, kept for comparison. A, B and C hold the axes and the specimen identical and change only the arrangement. D takes A's arrangement and changes the controls instead: its panel is rendered from a schema, and each axis gets the control its shape asks for. E puts C's colours and frame around D's schema and gives every short set a row of buttons instead of a row of words. Nothing on this page is in the system yet, and no showcase wears any of it.

Variant F

F · the unified rule: one canon of axes, a switch for yes and no, a select from five, and a toggle that fills its rail in equal shares when the labels fit

The layout is what ten systems already agree on, read off their live pages on 29 August: one card, lifted off the sheet by its own shadow, with the specimen fluid on a white stage at the left and a narrow grey rail of controls at the right, a single hairline between them, and the markup folded into the card's footer band. The rule over the controls is the one approved on 31 August and it now weighs three things about an axis, in this order. Its nature: yes or no is a switch, free text is a field. Its count: five values or more is our Select, because that is more than a person reads at a glance. And its budget: a set of two to four values is the toggle button only if the track it would draw can be paid for on one row of the rail at the width the rail has. Since 31 August the tracks in the rail fill it: every control spans the column and its halves split that column in equal shares, so a rail reads as one stack of lines instead of a stack of pills adrift at the left edge. Equal shares change the sum into a division. The room is spent first on the track's own furniture, the hairline twice, the inset twice and a gap between every pair, and what is left is divided by the number of values; the axis stays a toggle when its longest label, plus the padding on both sides, fits one of those shares. It is costed from the schema's own strings before anything is rendered, and costed again whenever the rail changes width. Above all of that sits the canon: the axes the system keeps meeting are named and settled once, so Size is a toggle and State and Colour are Selects on every component, and the arithmetic is only asked about the axes the canon has not met yet. An axis that does not apply is removed rather than greyed, the rare ones are behind one More, and Light or Dark left the rail for the stage it changes. One control here is a placeholder: the switch is a plain browser checkbox, because the system has no Switch until one is taken out of Figma and measured, and Figma is not open to us yet.

Variant F, second component

The same card, on a field

The same renderer given the field, because a rule that serves one component proves nothing. Look and State are Selects by the canon: five looks of a field are five faces picked once rather than a short scale, and states are read down a list rather than compared. Type has three values, so the canon makes it a toggle and the budget checks that its longest word, textarea, fits a share of the rail: it is only asked of the two looks that have a choice to make. Required is yes or no, so it is the placeholder switch. The error text exists only while the state is Error. Nothing else changes: the card, the rail, the rule and the footer band are the ones above.

Variant A

The panel and the stage

Variant B

The stage over a strip

Stage across the full width, axes under it in one strip. It puts the specimen first and the controls second, which is the opposite of the reading order the other two keep, and that is the thing to judge here.

Variant C

The console and the canvas

The axes are a console: one grey block on the left that reads as an instrument rather than as page text. The stage is framed and wears a head bar that names what is standing on it and holds the ground switch.

Variant D

The panel built by rule

Variant A again, so the layout is not what is being compared: the difference is that the panel is rendered from a schema and each axis gets the control its shape asks for. Short sets are a segment, five or more are a Select, a boolean is a segment of two. Icon position is not drawn until there is an icon, and the two axes nobody sets first are under More. Size moved off the Select on 29 August: four values is not a long list.

Variant D, second component

The same panel, on a field

The same renderer and the same rules, given the field instead of the button, which is the point of a schema: a showcase describes its component and gets a panel. Look is only drawn for the three faces that have a label style to choose, so the phone, the one time code and the password never offer a choice that does not exist.

Variant E

E · C colours, D logic, one control per axis type

C's console and framed stage, D's schema, and the control rule as it now stands: a short named set is a row of buttons with one pressed, a Select is for a long list, free text is a field. There is no Select in this panel at all: State has five values and still reads as buttons over two rows. Icon position, and the glyph under More, are not drawn until there is an icon.

Variant E, second component

The same panel, on a field

The same renderer given the field. Look has five values, so it is the one Select on the bench. State has six, and it is drawn twice on purpose, as a Select and as a row of buttons, both moving the same axis: the question of which reads better on a long set is answered by looking at them rather than by arguing. Type is only asked of the two looks that have a choice, and the error text only exists while the state is Error.
